# Engineering Design Notes & Architectural Rationale

This document details the engineering judgment, design trade-offs, failure modes, performance optimizations, and architectural principles behind the **YottaFlex Reusable Data Engineering Pipeline Framework**.

---

## 1. Architectural Philosophy & Technology Choices

### The Core Objective
The goal was not to build a bloated "framework" with dozens of heavyweight abstractions, but rather a **lean, complete, robust, and verifiable vertical slice** that demonstrates senior data engineering patterns:
1. Reusable ETL stages parameterized by dataset configuration.
2. Zero silent drops via comprehensive quarantine and row-level traceability.
3. True, verifiable idempotency (running the pipeline 1 or 10 times yields identical state).
4. Automated mathematical reconciliation across all stages.
5. High throughput (16,000+ rec/sec) achieved with standard library Python and SQLite.

### Why Standard Library Python + SQLite?
- **Zero Heavy External Dependencies**: Large dependencies (e.g., PySpark, Airflow, complex C++ wheels) introduce deployment friction, platform incompatibilities (especially on Windows), and unnecessary complexity for a coding challenge.
- **Python 3.13 Standard Library Capabilities**:
  - `csv` and `datetime` (Python 3.11+ `fromisoformat()` natively parses RFC/ISO-8601 strings with full timezone offsets).
  - `sqlite3` ships with the Python runtime, requires no separate daemon/server process, supports ACID transactions, and executes in-process with C-level speed.
  - Modern SQLite (v3.50+) provides full `UPDATE ... FROM ...`, CTEs, window functions, and advanced constraint checking.
- **When Would We Switch to Pandas or DuckDB?**
  - Pandas was deliberately avoided in the core ingestion path because:
    1. Dict-based row streaming consumes less overhead than constructing full DataFrame objects for small batches.
    2. Dataframe column type conversions can silently coerce `NaN` or parse bad strings unpredictably unless heavily guarded.
    3. Our standard-library streaming approach easily achieved **16,730 records/second**, making Pandas unnecessary for this scale.
  - DuckDB is an excellent alternative for analytical workloads; however, SQLite provides native embedded OLTP-style ACID transactions with robust `WAL` mode and zero third-party installation requirements.

## 2. Pipeline Stage Breakdown & Separation of Concerns

The pipeline follows a strict linear flow with decoupled stages:

```
Source CSV ──► CSVExtractor ──► SchemaValidator ──► BusinessValidator ──► DataTransformer ──► SQLiteLoader ──► Reconciler
                    │                   │                     │
                    ▼                   ▼                     ▼
                Quarantine          Quarantine            Quarantine
```

### Stage 1: Extraction & Fault-Tolerant Parsing (`extract.py`)
- **Row-level Error Tolerance**: In naive pipelines, a single malformed row (e.g., unquoted commas resulting in 7 fields instead of 6) crashes the entire pipeline. Our `CSVExtractor` catches column-count mismatches at the line level, records the 1-indexed source row number, and routes the defective row to `QuarantineManager`, allowing all remaining valid rows to proceed.
- **Encoding & BOM Handling**: Files generated by Windows Excel often contain UTF-8 Byte Order Marks (`\ufeff`). We use `utf-8-sig` encoding so header column names are never corrupted by invisible BOM characters.
- **Schema Drift Detection**: When new columns appear (e.g., `loyalty_tier` in `customers_sample.csv`), the extractor identifies them as extra columns, logs a drift warning, and includes them in the payload without crashing schema validation.

### Stage 2: Schema Validation (`validate.py`)
- Structural validation isolates syntax from semantics:
  - Missing required columns.
  - Empty values in non-nullable columns (e.g., `""`, `"null"`, `"None"`).
  - Basic type parseability (integer, float, finite numeric checks, and ISO-8601 timestamp regex).

### Stage 3: Domain Business Validation & Referential Integrity (`validate.py`)
- **Domain Business Rules**:
  - Email format validation via RFC 5322 regex.
  - Order amount bounds: strictly non-negative (`amount >= 0.0`) and finite.
  - Order status enum validation against `ALLOWED_ORDER_STATUSES`.
- **Referential Integrity Enforcement**:
  - For the `orders` dataset, before any database modification occurs, the validator loads the valid `customer_id` keys from the database.
  - Any order referencing an unknown customer is quarantined with code `ORPHAN_FOREIGN_KEY`.
  - In addition, the target database table enforces a strict foreign key constraint `FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ON DELETE RESTRICT` as defense-in-depth.

### Stage 4: Transformation & In-Batch Deduplication (`transform.py`)
- **Deterministic Deduplication Policy**:
  - If a single input file contains multiple rows with the same primary key (e.g., two entries for `ORD-00001` or `CUST-0001`), they cannot both be inserted.
  - Policy: The record with the later `updated_at` (or `created_at`) timestamp wins.
  - Tie-breaker: If timestamps are identical, the record appearing later in the source file (higher source row number) deterministically wins.
  - All superseded duplicates are collapsed and counted towards `in_batch_duplicates_resolved`, ensuring mathematical reconciliation remains exact.
- **Enrichment & Standardization**:
  - String trimming, email lowercasing.
  - Timestamps normalized to canonical UTC ISO-8601 strings (`YYYY-MM-DDTHH:MM:SSZ`).
  - `amount_cents` integer derivation: computed as `int(round(amount * 100))` to eliminate IEEE 754 floating-point inaccuracies in financial reporting.
  - Audit metadata: `_ingested_at`, `_source_file`, `_version = 1`.

## 3. Idempotency, Concurrency & Database Loading (`load.py`)

### The Staging Merge Upsert Pattern
To achieve high throughput, atomic transactions, and exact reporting of `inserted`, `updated`, and `skipped` counts, we use a **Temporary Staging Table Merge**:

1. A temporary table `_staging_<table>` is created matching the target table schema.
2. The batch of transformed records is bulk inserted into `_staging_<table>` via `executemany`.
3. Before executing mutations, the staging rows are partitioned into three disjoint sets:
   - **New records** (`inserted_count`):
     ```sql
     SELECT COUNT(*) FROM _staging_orders s
     WHERE NOT EXISTS (SELECT 1 FROM orders t WHERE t.order_id = s.order_id);
     ```
   - **Updated records** (`updated_count`):
     ```sql
     SELECT COUNT(*) FROM _staging_orders s
     JOIN orders t ON s.order_id = t.order_id
     WHERE s.updated_at > t.updated_at;
     ```
   - **Skipped records** (`skipped_count`):
     ```sql
     SELECT COUNT(*) FROM _staging_orders s
     JOIN orders t ON s.order_id = t.order_id
     WHERE s.updated_at <= t.updated_at;
     ```
4. DML statements are executed:
   - `INSERT INTO target ... SELECT ... FROM staging WHERE NOT EXISTS ...`
   - `UPDATE target SET ... FROM staging WHERE target.id = staging.id AND staging.updated_at > target.updated_at`
5. The temporary staging table is dropped and the transaction is committed.

### Why This Guarantees Idempotency:
- If an input file is re-run with identical data, every record matches the condition `s.updated_at <= t.updated_at`. As a result:
  `inserted_count = 0`, `updated_count = 0`, `skipped_count = N`.
- The database state remains byte-for-byte identical, with zero unintended duplicates.
- If a late-arriving or out-of-order record arrives with an older timestamp than what already exists in the database, it is safely skipped, preventing regression of newer state.

### Transaction Boundaries & Rollback
- Every load operation runs within an explicit `BEGIN TRANSACTION` block.
- If any database error occurs (e.g., constraint violation, disk I/O failure), `ROLLBACK` is immediately triggered, leaving the target table clean.
- The pipeline catches the exception, updates `metrics.finish(status="FAILED", error_message=str(e))`, and records the failed run in `pipeline_runs`. The failure is never silently swallowed.

### Transient Error Handling (`with_retry`)
- SQLite operates via file-level locking. Under concurrent access, operations can encounter `sqlite3.OperationalError: database is locked`.
- We implement a `@with_retry` decorator using exponential backoff with configurable retries (default 3 retries, starting at 100ms with a 2x multiplier).

## 4. Performance Optimizations & Empirical Measurements

### Optimizations Implemented:
1. **Write-Ahead Logging (WAL)**: `PRAGMA journal_mode = WAL;` eliminates reader/writer blocking and dramatically accelerates disk commits.
2. **Synchronous Mode Normal**: `PRAGMA synchronous = NORMAL;` provides durability while removing redundant disk sync operations.
3. **In-Memory Staging**: `PRAGMA temp_store = MEMORY;` ensures temporary merge tables are stored in RAM.
4. **Batched Staging Inserts (`executemany`)**: Replaces row-by-row queries with single parameterized SQL statements.

### Empirical Measurements:
We conducted actual empirical measurements comparing naive row-by-row autocommit inserts against our optimized staging merge on the same hardware:

| Implementation Mode | Batch Size | Total Elapsed Time | Measured Throughput | Speedup Factor |
|:---|:---:|:---:|:---:|:---:|
| **Naive Baseline (Autocommit row-by-row)** | 500 rows | 3.6019 s | 138.8 rec/sec | 1.0x (Baseline) |
| **Optimized Pipeline (Staging Merge + WAL)** | 500 rows | 0.0190 s | 26,274.2 rec/sec | **189.3x faster** |

### Scale Benchmark (200,000 Records Total):
Tested on Windows 11 with Python 3.13:
- **Total Records Processed**: 200,000 (100,000 customers + 100,000 orders)
- **Dataset Generation Time**: 2.03 seconds
- **End-to-End Pipeline Runtime**: 11.95 seconds
- **Overall Pipeline Throughput**: **16,730.41 records/second**
  - Customers: 4.78 seconds (20,902 records/sec)
  - Orders: 6.69 seconds (14,948 records/sec)
- **Database Reconciliation Result**: **100% PASSED** (0 orphan orders, 0 duplicates, 100% valid derived cents).

## 5. Mathematical Reconciliation System

Data pipelines must prove their correctness through invariant assertions, not assumptions. Our `ReconciliationEngine` enforces three mathematical conservation laws:

1. **Record Conservation Law**:
   $$\text{Total Input Rows} = \text{Valid Rows} + \text{Rejected Rows}$$
2. **Ingestion Disposition Conservation Law**:
   $$\text{Valid Rows} = \text{Inserted Rows} + \text{Updated Rows} + \text{Skipped Rows} + \text{In-Batch Duplicates Resolved}$$
3. **Quarantine Auditability Invariant**:
   $$\text{Rejected Rows (Metrics)} = \text{Count of Quarantined Records in DB for this Run ID}$$
4. **State Invariants**:
   - $\text{Count}(\text{PK}) = \text{Count}(\text{DISTINCT PK})$
   - $\text{Count}(\text{Orphan Orders}) = 0$
   - $\text{Count}(\text{Negative Amounts}) = 0$
   - $\text{Count}(\text{Invalid Statuses}) = 0$

## 6. Known Limitations & Production Roadmap

| Current Architecture | Production Evolution |
|:---|:---|
| **Local SQLite File Persistence** | Migrate `SQLiteLoader` to Postgres, Snowflake, or BigQuery via SQLAlchemy or native database connectors. |
| **In-Memory Referential Key Cache** | For billions of customers, replace `get_existing_customer_ids()` with a Redis bloom filter or a database semi-join query (`WHERE customer_id IN (SELECT id FROM staging)`). |
| **Local File / Batch Ingestion** | Wrap pipeline in Apache Airflow / Dagster DAGs or deploy as an event-driven AWS Lambda / Google Cloud Function triggered by S3 / GCS file arrival. |
| **Single-Machine Concurrency** | Use multiprocessing or ray/dask workers for distributed parallel chunk extraction across massive file partitions. |
